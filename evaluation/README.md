# TrialUnity Retrieval Evaluation

A small, reproducible benchmark that answers one question: **does hybrid (BM25 +
embeddings + structured signals) retrieval actually rank trials better than either
signal alone?** It does not evaluate structured eligibility or ESR quality -- see
[Why eligibility and ESR are evaluated separately](#why-eligibility-and-esr-are-evaluated-separately).

Run it with:

```bash
python -m evaluation.run
```

No network access is used or required: the benchmark, the trials, and the
embedding model are all local. Results print to the console and are written to
`evaluation/results/latest.json` and `evaluation/results/latest.md` (use
`--no-write` to skip that, or `--out <dir>` to write elsewhere).

## Benchmark construction

`evaluation/fixtures/benchmark.json` holds **16 synthetic cases** (no real patient
records, no real registered trials -- every condition/trial name is invented for
this benchmark). Each case is one patient profile plus 4-5 candidate trials with a
hand-assigned relevance grade. Categories, each represented by 2+ cases:

| Category | What it tests |
| --- | --- |
| `exact_condition` | Trial text names the same condition as the query |
| `related_terminology_low_lexical_overlap` | Acronym vs. spelled-out term, lay term vs. clinical term, rare-disease naming -- near-zero keyword overlap despite being the same concept |
| `treatment_preference` | Ranking should favor a patient's preferred intervention/drug over an otherwise-equal trial |
| `location_preference` | Ranking should favor sites near the patient, including decentralized/remote trials |
| `phase_preference` | Ranking should favor the patient's preferred trial phase |
| `eligibility_incompatibility` | The most textually relevant trial is structurally ineligible for the patient (age/sex) -- proves relevance ranking is not contaminated by eligibility |
| `distractor` | Several plausible-looking but wrong-condition trials, to catch overconfident partial matches |

Every case includes at least one grade-0 distractor. Relevance grades:

- **2** -- highly relevant (right condition, and matches what the patient asked for)
- **1** -- partially relevant (related condition, or right condition but missing a stated preference)
- **0** -- irrelevant

Grades were assigned by hand from the patient/trial text and were not touched
after seeing any evaluation results (see [Limitations](#limitations)).

## Metric definitions

All three are computed per case and averaged (unweighted mean) across all 16 cases.
"Relevant" for Recall/MRR means grade >= 1 (`evaluation/metrics.py:RELEVANT_THRESHOLD`).

- **Recall@K** -- fraction of all relevant trials for that case that appear in the top K.
- **MRR** -- 1 / (rank of the first relevant trial), 0 if none appear.
- **nDCG@K** -- `DCG@K / IDCG@K` using graded relevance (`(2^rel - 1) / log2(rank + 1)`), which is the more informative metric here since it distinguishes grade 1 from grade 2 and rewards getting the *best* trial to the top, not just *a* relevant one. `K = 3, 5`.

## Ablation: lexical vs. dense vs. hybrid

Each benchmark case is ranked three ways over the exact same candidates:

- **A. lexical** -- `BM25Retriever` alone, ranked purely by normalized BM25 score.
- **B. dense** -- `DenseRetriever` alone (`all-MiniLM-L6-v2`), ranked purely by cosine similarity.
- **C. hybrid** -- the production `HybridRetriever` (lexical + dense + structured condition/intervention/phase/location signals).

The query text for A and B is built the same way `HybridRetriever` builds it
internally (condition + notes only) -- structured preferences (location/phase/
intervention) are *not* part of the text query in production either, so A and B
correctly have no way to use them. That's not a benchmark artifact; it's what the
app actually does, and it's exactly the gap hybrid's structured signals exist to close.

### Current results

_(Generated by `python -m evaluation.run`; see `evaluation/results/latest.md` for
the full per-category table and `latest.json` for per-case diagnostics.)_

| system | mrr | recall@3 | ndcg@3 | recall@5 | ndcg@5 |
| --- | --- | --- | --- | --- | --- |
| lexical | 1.0000 | 0.9479 | 0.8803 | 1.0000 | 0.9018 |
| dense | 1.0000 | 1.0000 | 0.8806 | 1.0000 | 0.8806 |
| hybrid | 1.0000 | 0.9688 | 0.9586 | 1.0000 | 0.9751 |

**Hybrid has the best nDCG** (the metric that actually distinguishes a highly
relevant trial from a merely partial one) and ties for best MRR/Recall@5. That
mostly comes from the categories it's structurally supposed to win: whenever the
benchmark rewards a treatment/location/phase preference, lexical-only and
dense-only have no mechanism to use that preference at all (it isn't in their text
query), so hybrid wins there by construction, not by benchmark tuning.

### Where hybrid does *not* win (reported honestly)

- **`paraphrase-nsclc-acronym`**: dense-only scores nDCG@5 = 0.920 vs. hybrid's
  0.877. The relevant trial that uses "NSCLC" with zero other shared words gets
  buried at rank 4 in both lexical-only *and* hybrid, because BM25 contributes
  exactly 0 for it and that drags the blended hybrid score down even though its
  dense/semantic score alone was reasonable. Pure dense ranks it above the
  irrelevant distractor; hybrid does not. Concretely: with a fully lexically
  disjoint but semantically valid match, hybrid's 0.30 lexical weight can outweigh
  a correct dense signal. See `evaluation/results/latest.json ->
  cases[paraphrase-nsclc-acronym].diagnostics` for the exact per-signal breakdown.
- **`eligibility-age-restricted`** / **`eligibility-sex-restricted`**: lexical-only
  scores nDCG@5 = 1.0 vs. hybrid's 0.951 on both. These cases have two grade-2
  trials with slightly different text; hybrid's added semantic/structured terms
  shuffle their exact order slightly. The gap is small (both trials are still
  ranked in the top 2) and doesn't change which trials are surfaced as relevant.

These are read directly off `evaluation/results/latest.json`, not tuned away --
per the brief, the benchmark and the retrieval code were not adjusted to make
hybrid win. The NSCLC case is a legitimate, minor weakness worth remembering: a
future iteration could look at down-weighting lexical when it is the *only* zero
signal for an otherwise semantically strong candidate.

## Ranking diagnostics

`evaluation/results/latest.json -> cases[*].diagnostics` (and `evaluate_case()` in
`evaluation/ablation.py`) captures, per case: the expected relevant trial IDs, and
the full hybrid ranking with each trial's normalized lexical score, semantic
score, weighted structured contribution, matched terms, and relevance grade --
enough to see exactly why a trial ranked where it did without re-running anything.

## Why eligibility and ESR are evaluated separately

This benchmark measures one thing: **is the ranking order good?** It deliberately
does **not** touch:

- **Structured eligibility** (`backend.app.services.eligibility`) -- a
  deterministic compatible/incompatible/unknown judgment, not a relevance score.
  It's already covered by `tests/test_eligibility.py`'s parametrized correctness
  tests, which is the right kind of test for a rule-based classifier, not an IR
  ranking metric like nDCG.
- **ESR** (`backend.app.services.equity`) -- explicitly not a relevance signal (see
  the README's "Equity / Access Representation" section) and must never be scored
  against relevance grades, or that would imply representation/access should
  influence ranking, which is exactly what ESR's design forbids in this phase.

`evaluation/esr_checks.py` instead runs three lightweight structural checks
(also exercised in `tests/test_evaluation.py`):

1. **Deterministic** -- `compute_esr` returns the identical result for the same inputs.
2. **Missing evidence changes coverage, not score** -- removing enrollment data lowers `evidence_coverage` but never forces `score` to 0.
3. **Does not change clinical ordering** -- attaching ESR-only evidence (enrollment distributions) to a trial never changes `HybridRetriever`'s ranking, because retrieval never reads those fields.

If ESR's own quality (e.g. "is this a good measure of access") needs validating
later, that's a different kind of evaluation -- grounded in real-world Phase 5
demographic/benchmark data -- and belongs in its own framework, not bolted onto
this one.

## Limitations

- **16 cases is a portfolio-scale benchmark, not a statistically powered one.**
  A ~0.06-0.09 nDCG gap between systems here is illustrative, not a claim of
  statistical significance -- there's no confidence interval to report with this
  few, hand-picked cases, and a couple of cases flipping would change the ranking
  of "best system."
- Every trial is synthetic; results say nothing about performance on the messier
  text real ClinicalTrials.gov records contain.
- Relevance grades are one author's judgment, not multi-rater consensus, so
  there's no inter-rater agreement figure to report.
- Recall/MRR collapse grade 1 and grade 2 into one "relevant" bucket; nDCG is the
  metric that actually reflects the graded labels, and is weighted accordingly in
  this write-up.
- `pytest`-driven checks (`tests/test_evaluation.py`) substitute a fast
  deterministic hash-based embedding model (see `tests/conftest.py`) so the suite
  doesn't need to load the real model; only `python -m evaluation.run` produces
  the numbers reported above, using the actual production `all-MiniLM-L6-v2` model.
